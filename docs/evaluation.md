# 评测记录

本轮（改善检索与召回）建立的固定评测。数据全部是代码里写死的合成内容，编号显式指定，不读个人库、不依赖本机记录编号。

**这些预期是写测试时自己定的，还没有经过逐条人工审核**，所以它不是人工标注数据集，只能说明「在下面这份定义下，新旧实现表现如何」。

## 一、检索评测

数据与用例：`internal/repository/search_eval_test.go`。12 条有内容的记忆、40 条更新的无关填充、6 条只命中查询一部分的干扰项；旧实现（上一轮的按空白切词 + 按 id 倒序）原样复制在同一文件里做对照。

指标口径：

- **K = 5**，即每条查询只取前 5 条。
- **Hit@5**：前 5 条里出现了该查询的任一相关记录，即算命中。分母是**有相关目标的 9 条查询**。
- **Recall@5**：前 5 条覆盖了该查询相关目标的多少，再对那 9 条查询取**宏平均**——每条查询等权，不按相关目标的条数加权。
- **3 条没有相关目标的查询不参与 Recall 的平均**：Recall 的分母是相关目标数，没有目标就无从计算，把它们算进来只会让分母虚增。这 3 条只看**误召回**——前 5 条里返回了任何一条，就算一次误召回。

「预期相关」一列是 `evalCases` 里每条查询的 `want`，`—` 表示这条查询本来就不该有相关结果。

| 用例 | 查询 | 预期相关 | 旧 | 新 |
| --- | --- | --- | --- | --- |
| 中文完整问句 | 我周末喜欢跑步这件事你还记得吗 | `1` | `[]` | `[1 58 57 56 55]` |
| 中文完整问句无空格 | 我学的Go最近怎么样了 | `3` | `[]` | `[3]` |
| 简短关键词 | 咖啡 | `12` | `[12]` | `[12]` |
| 单字查询 | 猫 | `2` | `[2]` | `[2]` |
| 多词查询 | 早上 起床 习惯 | `6` | `[6]` | `[6]` |
| 中英文混合 | VS Code 代码 | `10` | `[10]` | `[10]` |
| 较旧相关 vs 较新无关 | 跑步 周末 | `1` | `[58 57 56 55 54]` | `[1 58 57 56 55]` |
| 重复词 | 跑步 跑步 跑步 | `1 53 55 57` | `[57 55 53 1]` | `[57 55 53 1]` |
| 无字面重合的同义表达 | 我养的那只宠物现在怎么样了 | `2` | `[]` | `[]` |
| 已失效记忆 | PyCharm | — | `[]` | `[]` |
| 无相关结果 | 量子力学 拓扑绝缘体 | — | `[]` | `[]` |
| 通配符查询 | % | — | `[58 57 56 55 54]` | `[]` |

```
Hit@5    旧 5/9    新 8/9          有相关目标的 9 条查询
Recall@5 旧 0.56   新 0.89         宏平均，同样这 9 条
空目标查询里出现误召回的条数：旧 1，新 0    （3 条查询，其中只有「通配符查询」这一条在旧实现下误召回）
```

Hit@5 和 Recall@5 在这份数据上数值相等（都是 5/9 与 8/9），但这是数据形状凑出来的，不是定义上必然：9 条有目标的查询里有 8 条只有 1 个目标，唯一多目标的「重复词」在两种实现下都 4 个全中（4/4），没有任何一条出现「只找回一部分」。只要将来加入一条部分命中的查询，两个数就会分开。

**改善**来自两类缺陷：

1. 中文整句。旧实现用 `strings.Fields` 切词，中文没有空格，整句被当成一个词去 LIKE，几乎不可能命中；新实现按二元组切，`我周末喜欢跑步这件事你还记得吗` 会拆出「喜欢」「跑步」等片段。
2. 排序。旧的只按 id 倒序取前 5 条，`跑步 周末` 里唯一同时命中两个词的记忆 1 被较新的部分命中记录挤了出去（旧结果 `[58 57 56 55 54]` 全是只命中一个词的）；新实现按命中词数排序，记忆 1 回到首位。

**没有观察到退化**：简短关键词、单字、多词、中英文混合、重复词这几条新旧一致；已失效记忆与无相关结果两条新旧都返回空。三条无目标查询里唯一的差异在通配符查询：旧实现在 `LIKE '%'` 下把整个库都算命中、返回 5 条，新实现返回空——上面那个「旧 1」的误召回就是它，这里是改善不是退化。

**未解决的样例**（保留在用例里，照常跑、照常打印）：

- `我养的那只宠物现在怎么样了` 对记忆「用户养了一只猫，名字叫豆豆」——字面零重合，新旧都召不到。中文切词解不了同义表达，这一条是路线本身的边界。
- `跑步 跑步 跑步` 重复词：去重后只剩一个词，排序退化成按新旧排，记忆 1 排在 3 条只命中「跑步」的更新记录之后。这是设计取舍（同分保持新的在前），不是缺陷，但它在「重复强调同一个词会不会提高权重」这个问题上给出了否定答案。

**适用范围**：一次查询最多拆 16 个词，粗筛最多取 200 条候选再在内存里排序。这是个人量级数据下的方案，不是为大规模检索设计的，也没有向量召回。

## 二、Formation 的记忆候选

分两步验证，**两者不能互相代替**：

| 问题 | 覆盖方式 | 结果 |
| --- | --- | --- |
| 服务端有没有把那条久远的旧记忆交给模型 | `internal/service/formation_candidates_test.go`（假模型 + 真实数据库） | 通过。相关旧记忆进了输入，无关旧记忆没进，总条数不超过 12 + 8 |
| 模型自己会不会作出正确的更新 | `internal/service/realcheck_agent_test.go` 场景四（真实模型，不连库） | 通过。输入同一条消息，模型输出 `SUPERSEDE memory:1`，新内容「用户打算每周跑步一次」；校验后目标记录正确 |

前者证明的是「候选里有它，所以模型给出的替换不会被校验丢掉」，后者证明的是「模型看着这份候选确实会做这个判断」。任何一条单独都不能说明另一条。

## 三、生活记录的按需召回

`internal/service/realcheck_agent_test.go`，真实模型 + 真实数据库 + 完整 `ChatStream` 链路，打印模型的实际工具轨迹与回答。合成数据：10-01/03/05 三次跑步、10-07 明确没去、10-10 打算爬山、一条「三年前」参加了校运会（发生日期未知）。

**场景一：需要工具** —— 「我最近跑步的情况怎么样？」

PASS。模型分两步调用了 4 次 `recall_life_records`（先按内容查、再按日期区间查），回答逐条对上了记录：10-01 五公里、10-03 三公里、10-05 八公里、10-07「没去」、10-10「打算去爬山（还没到）」，并主动说明「8 号、9 号我这边没有记录，不确定你是没跑还是没提」。**区分了完成、否认与计划，也没有把没记录当成没发生。**

**场景二：不需要工具** —— `TestRealAgentSkipsToolsWhenUnnecessary`，五个自包含任务各跑一次完整链路：翻译、造句、润色、算数、写代码。

PASS（5/5）。五次都是 0 次工具调用。上一轮这里只有翻译一个样例并且是 FAIL——模型仅因为句子里出现了「跑步」就查了库。这一轮改的是表述方式而不是分流规则：工具说明与 system prompt 里写的是「当前输入已经足够完成任务时就别查」，没有写成「出现某类词就禁用工具」。**本项目没有采用关键词分流，也没有意图分类器：是否需要历史上下文，由模型自己判断。**

这条结论只覆盖这五个样例。模型会不会在别的自包含任务上多查一次，没有测，不能从这五次推广出去。

**场景三：查不到的时候** —— 「我上周去游泳了吗？」

PASS。模型先按内容查（0 条）、再按上周的日期区间查（只有两条跑步），回答是「游泳这件事我这边查不到记录……不过『没有记录』不等于『没去过』」。

**场景五：必须查历史但没有关键词** —— 「我最近都在忙些什么？」

PASS。问题里没有任何可以被拿来匹配记录的字眼，模型仍然调了两次 `recall_life_records`（先按发生日期区间、再按提及日期区间），第二次请求就带着结果作答，逐条对上了 10-01/03/05 的三次跑步、10-07「没去」和 10-10「打算去爬山」，并补了一句「这只是我这边存下的记录，不代表你别的活动没有」。这条与场景二合起来才说明问题：**该查的时候查了，不该查的时候没查，两次都不是靠关键词。**

**这一节的结论只到模型输出与工具轨迹**：工具确实被真实模型调用、真实数据库返回了结果、返回结果确实影响了解释。这三个场景验证的是**模型会不会挑对工具、回答有没有拿记录当依据**；持久化、事务与断流恢复是另一类问题，由带替身的专项用例覆盖，真实模型场景不能代替它们。回答是否「更贴心」也不在评测范围内。

## 四、状态日历与长期记忆管理

这两块都是行为验证，用假模型 + 真实数据库，跑在 `internal/service/calendar_test.go` 与 `internal/service/memory_test.go`。测的是**规则、缓存、并发与作用范围**，不是模型整理得好不好。

### 模型调用次数

| 操作 | 调用次数 | 用例 |
| --- | --- | --- |
| 打开一个月份（含读取待整理清单） | 0 | `TestDaySummaryModelCallCounts` |
| 某一天第一次整理 | 1 | 同上 |
| 输入没变，重复整理同一天 | 0（复用已有结果） | 同上 |
| 那天的聊天或线索变了之后再整理 | 1（额外一次） | 同上 |
| 有聊天但明显没有状态线索的一天 | 0 | `TestDaySummarySkipsModelWhenNoClue` |
| 当天没有可见聊天 | 0 | `TestCalendarChatWithoutClue` |

「打开月份 0 次」说的是**接口**，不是「打开日历页不花钱」，这两件事要分开看：读月份的接口只读库、并返回一份「需要整理的日期」清单，真正的整理由页面按这份清单逐个触发——那个月有几天待整理，页面打开后就会补上几次模型调用。表里后四行量的正是这一步。所以**打开一个月份不会一次性生成整年数据**，聊天主链路上也没有增加任何固定调用；已经整理过、输入也没变的日子不会重复调用。

### 日期归属与状态判定

| 要查的事 | 用例 | 结果 |
| --- | --- | --- |
| 月份天数不硬编码（31/28/29/31/31/30） | `TestCalendarMonthShape` | 通过，含闰年二月 |
| 跨午夜归到哪一天 | `TestCalendarDayBoundary` | 通过，23:30 与次日 00:30 各归各天 |
| 换业务时区后日期归属跟着变 | `TestCalendarTimezoneChangesDayAttribution` | 通过，上海时间 10-05 23:30（同一时刻在东京已是 10-06 00:30）在 Asia/Tokyo 下归到 10-06 |
| 只有一条线索也照样用 | `TestCalendarClueAttribution` | 通过 |
| 「昨天很焦虑」不算今天焦虑 | `TestCalendarClueAttribution` | 通过 |
| 只有聊天、没有线索 | `TestCalendarChatWithoutClue` | 通过，返回「线索不足」而不是编一个标签 |
| 未来计划不会变成未来某天的心情 | `TestCalendarRejectsFutureDays` | 通过，整理未来日期直接拒绝 |
| 输入过长时的截断标记 | `TestDaySummaryInputTruncation` | 通过，`input_truncated` 如实置位 |
| 不带月份时默认给当月 | `TestCalendarMonthDefaultsToCurrentMonth` | 通过 |

**哪条线索算哪一天**，规则是机械的，写在 `clueDay` 里：

| 线索 | 归到哪天 |
| --- | --- |
| `mood` | `occurred_on`；当 `date_precision='unknown'` 且 `date_text` 为空时用 `mentioned_on` |
| `activity` 且 `state` 是 `done` / `negated` | `occurred_on` |
| `activity` 且 `state='planned'` | **排除** |
| `goal` / `date` / 主体不是用户本人 / 已被纠正的 | **排除** |

日期归属在 Go 里按 `APP_TIMEZONE` 归桶，不走 SQL 的 `DATE(created_at)`，也不做 `CONVERT_TZ`。排除 `planned` 是为了「明天想去爬山」不变成明天的心情；排除主体不是用户的，是为了别人的状态不进自己的日历。

回退到 `mentioned_on`（说出口的那天）只有一种情形：`mood` 线索的 `date_precision='unknown'` **且**原话里没有任何时间说法（`date_text` 为空）。其余情况都不回退。`activity` 尤其不是「发生日期未知就按说的那天算」——已完成或明确否认的活动只在 `occurred_on` 有值时才归到那一天，未知就归不到任何一天，只能从「提及日」的角度被查到。这条回退依赖模型给出的日期精度，**通常对，但不保证**。


### 缓存失效、失败与并发

| 要查的事 | 用例 | 结果 |
| --- | --- | --- |
| 生成失败不覆盖上一次的成功结果 | `TestDaySummaryFailureKeepsPreviousResult` | 通过 |
| 第一次就失败时不留下卡在「整理中」的行 | `TestDaySummaryFailureWithoutPreviousResult` | 通过，落到「整理失败」并可重试 |
| 手动标签不被迟到的自动结果覆盖 | `TestManualLabelWinsOverLateGeneration` | 通过，`result_digest` 保持为空 |
| 取消手动设置后恢复自动 | `TestClearManualLabelRestoresAutoResult` | 通过 |
| 没有聊天的日期不接受手动标签 | `TestManualLabelRejectsDayWithoutChat` | 通过，返回 400 且状态不变 |

缓存不是靠「记录条数没变」判断的：指纹里带了业务时区、当天可见用户消息的编号，以及每条线索的 `id | status | clueDay | content`，所以**新增一条聊天、纠正一条线索、把线索置为失效，都会让那天的结果过期**；换业务时区同样会。`dayDigest` 是这套判断的唯一来源。

数据库层面的并发保护用条件更新实现（`ClaimDayState` 抢租约、`ApplyDayState` 带 owner + digest 复核），语义等价于 `WHERE attempt_status='running' AND attempt_owner=? AND attempt_digest=?`，影响行数为 0 就说明这次执行已经不是当次认领的了，直接丢弃。**没有引入 Redis、队列或调度平台。**

### 记忆的纠正与忘记

| 要查的事 | 用例 | 结果 |
| --- | --- | --- |
| 列表默认只看有效记忆 | `TestMemoryListDefaultsToActive` | 通过 |
| 条数受限时不假装已展示全部 | `TestMemoryListMarksTruncation` | 通过，返回 `truncated` |
| 纠正后旧原话不再证明新内容 | `TestCorrectMemoryKeepsEvidenceHonest` | 通过，新记忆没有 `memory_sources` 行 |
| 来源里给出用户自己写的那句和时间 | `TestCorrectMemoryKeepsEvidenceHonest` | 通过，`action` / `new_content` / `created_at` 都在 |
| 忘记后不再进入召回 | `TestForgetMemoryRemovesFromRecall` | 通过 |
| Formation 不重新强化用户刚改过的记忆 | `TestFormationSkipsMemoriesTheUserJustChanged` | 通过 |
| Formation 遇到已删除的记忆不整批失败 | `TestFormationSkipsMissingMemory` | 通过 |

纠正的做法是**新增一条** `origin='user_corrected'` 的记忆，把原来那条标成 `corrected` 并指向新的那条；**没有伪造一条聊天消息来充当证据**，旧聊天原文只作为「你改之前的说法」列在来源里，并且明确标注它不用来证明现在的内容。忘记是软删除（`status='forgotten'`），重复操作幂等，原始聊天和其他生活记录都保留。

来源里的纠正记录原来只给了**被换掉的旧内容**，读的人无从知道现在这条的依据是什么。现在那一行带上 `action` 和 `new_content`，用户自己写的那句连同时间一起返回，旧的那句由 `content` 单独带着。Agent 那条路径读的是同一个入口，所以拿到的 JSON 是这样的（本轮实际跑出来的）：

```json
{"memory_id":2,"sources":[{"source_type":"correction","content":"用户讨厌开会",
 "created_at":"2026-10-10T11:06:42+08:00","action":"correct","new_content":"用户不喜欢连着开长会"}]}
```

`new_content` 是用户这次输入的，`content` 是它替换掉的旧说法。前端照这个分支渲染：有 `new_content` 时把它当正文，旧的那句退成一行小字「改之前是：……」。`get_memory_source` 的工具说明也写明了这个区别，免得模型反过来拿旧句当依据。

### 界面验收（无头浏览器实跑）

用 Edge 的无头模式把页面渲染出来看，不是靠「构建通过」下结论。数据全是编造的对话（四天的示例聊天、几条生活记录与长期记忆），导进一次性的 `memora_test`；验收后端连的也是这个库。那份样例数据没有留在仓库里，所以下面这些画面不是照着仓库里的某个文件能原样重放的。

跑之前先把三件事做实了，都是实际渲染暴露出来的：

| 问题 | 怎么发现的 | 修法 |
| --- | --- | --- |
| 首次打开日历是一整页「日历参数不合法」 | 页面还没有月份，只能传空，服务端把空当成参数错误 | 不带月份就是当月，按业务时区取 |
| 月份接口一返回就整页报错 `Cannot read properties of null` | 列表字段在响应里是 `null`，前端读它的长度时崩掉 | 服务端返回了 nil 切片，被编码为 `null`；改为返回非 nil 空切片，编码为 `[]` |
| 可以在没有聊天的日期上设标签 | 直接调接口试出来的：那天会变成「已有结果 + 用户设置」，看着像那天聊过 | 服务端拒绝（400），界面也不给这个入口 |

同一个月份打开两次，第二次 `pending_days` 为空、那天仍是 `ready` + `auto`，说明页面上那一次整理之后确实走了缓存，不会重复调用模型。

**跨年切月**单独查了一次：从打开时的 2026-10 连点 10 次「上个月」，界面、网格和发出去的请求三样对上，再往后跨一年回来。同源的探针页把结果直接打在页面上，后端那边另有一份自己的请求记录，两边独立。

| 检查 | 界面显示 | 网格 | 发出去的请求 | 结果 |
| --- | --- | --- | --- | --- |
| 2026-01 的前一个月 | `2025 年 12 月` | 31 格，`2025-12-01`～`2025-12-31`，前面空 0 格 | `month=2025-12` | 一致 |
| 2025-12 的后一个月 | `2026 年 1 月` | 31 格，`2026-01-01`～`2026-01-31`，前面空 3 格 | `month=2026-01` | 一致 |
| 再退回 | `2025 年 12 月` | — | `month=2025-12` | 一致 |

后端日志里那一段是按 `2026-09 … 2026-02 / 2026-01 / 2025-12` 的顺序来的，**没有出现 `2026-00`**；前面空格 0 和 3 也分别对得上 2025-12-01 是周一、2026-01-01 是周四。另外首次进页面发的是不带参数的 `/api/calendar/month`，由服务端补成当月，和「不带月份就是当月」那条修法一致。

验收用的后端 `LLM_BASE_URL` 指到一个关着的本地端口：这能说明的只有两件事——**整个过程没有产生真实的在线模型调用**，以及**模型不可用时那条失败路径确实被走到了**；它不说明真实模型返回的内容被验证过（那部分在第五节）。失败那一路的实际表现是：10-05 那天是演示数据里唯一有聊天又有线索的一天，页面确实为它发了 1 次整理请求，失败后界面状态是 `failed` 并带着可读的原因，`pending_days` 随即变空（不会一直重试），同一个月里用户自己设过标签的 10-07 仍是 `ready`。除了那 1 次，2025-12 和 2026-01 都没有聊天，**一次整理请求都没发**。

看过的画面：三页的入口与切换、日历整月的排布与今天/选中/各状态的层次、某一天的自动结果与手动结果（标签、摘要、线索、原话）、记忆列表，以及改写过的那条记忆展开来源后的样子：正文是**用户自己写下的那句**，旧句退成一行小字「改之前是：……」。这一张是改完来源结构之后重新渲染确认的，不是沿用上一轮那张。窄屏用 390px 宽的视口单独渲染过（无头模式会强行把窗口撑到约 500px，所以是套一层定宽 iframe 拍的），日历、当天详情和记忆卡片都没有横向溢出，「线索不足」这类文字会换行。

**没看到的**：真机触屏、滚动惯性、键盘 Tab 顺序的实际走位。跨年那一次是用脚本点按钮做的，没有逐步用键盘走一遍。点击和回车触发是按可聚焦的按钮写的，但没有逐步验证过。这些不算已验证。

## 八、测试环境与数据库隔离

这些细节不影响评测结论，放在这里而不是 README。

**为什么必须 `-p 1`。** 所有测试包共用 `MEMORA_TEST_DSN` 指的那一个库，而每个包的测试进程首次连接时会 `DROP` 再重建它、重跑迁移。并行跑测试包时，一个进程正在重建库、逐条跑迁移的窗口里，另一个进程正好连上去，就会看到不完整的表结构（典型报错是 `Unknown column`）或撞上约束冲突，表现为随机失败。`-p 1` 让测试包串行，绕开这个窗口。**这是绕过，不是修复——共享库的隔离缺陷仍然存在。** 也不要在跑测试的同时运行另一个使用同一个库的测试命令或验收服务。

`-p 1` 只约束测试包之间的并发，不影响 `t.Parallel()`，也不等同于 `-parallel`，所以包内并发行为的测试照常有效。

**清表顺序。** 每个用到测试库的测试开始前会 `DELETE FROM` 六张表：`memory_corrections`、`life_records`、`memory_sources`、`memories`、`chat_messages`、`day_states`。顺序按外键依赖倒序排列，`memory_corrections` 指向 `memories`，所以它排在最前。

**库名规则与切库防护。** 分三个环节，作用时机不同：

1. **写入之前的目标检查**：只认 `MEMORA_TEST_DSN`，不存在回退到 `DB_NAME` / `DB_PASSWORD` 的路径；库名必须非空、以 `_test` 结尾、且只含标识符安全字符，否则直接报错退出，不猜一个「差不多」的库名。这两项都在连库、建库、跑迁移之前完成。
2. **迁移语句的处理**：迁移文件里的 `use` / `create database` 会被丢弃，不让脚本自己把连接切到别的库上。
3. **迁移之后的核验**：迁移跑完、以及每次连接之后都会 `SELECT DATABASE()` 复核连接停在哪个库上，不一致就报错。这一条发生在语句已经执行之后，是事后确认，不是事前拦截——万一前两条有遗漏，它只能报告「停错了库」，不能阻止切换本身。

`migrations/001_schema.sql` 本身已经不含切库语句，规则 2 是兜底：以后谁把 `use <库名>` 加回迁移里，它会被丢掉而不是被执行。`internal/testsupport/db_test.go` 里有一条用例专门扫真实迁移目录，一旦有人把 `use <库名>` 加回去就会失败。
